# Design Log

One entry per real choice: date, decision, why, alternative considered.
This feeds the report's "trade-offs" and "alternative design" sections.

| Date | Decision | Why | Alternative considered |
|---|---|---|---|
| 22 Oct | `ArrivalSchedule.customersArrivingAt(turn)` returns `List<Customer>` (empty if nobody arrives) instead of a single `Customer` or `null` | No null checks in the controller; more than one arrival per turn becomes a schedule change, not a controller change | Return `Customer`/`null` (draft diagram); `Optional<Customer>` |
| 22 Oct | `ConsoleUI.showFinalResult` takes the `Objective` | UI must show which targets passed/failed without re-implementing the win rule | Pass three booleans; UI re-checks thresholds itself (duplicates the rule) |
| 22 Oct | Loop over a copy of the customer list in step 5 | Customers leave mid-loop; removing from the list being iterated throws `ConcurrentModificationException` | `Iterator.remove()` |
| 23 Oct | Keep Raghav's Customer API (`seat()`, `orderTaken()`, `serve(turn)`, `finishEating(turn)`, `markPaid(turn)`, `decreaseSatisfaction()`, statuses `WAITING_FOR_FOOD`/`SERVED`) | Already written and tested by its owner; renaming gives no design gain | Rename to the draft diagram's names (`seatAt`, `placeOrder`, ...) |
| 23 Oct | Customer does not hold its Table/Order; `Table` holds the occupant, `Order` holds the customer, `Restaurant` looks them up | Matches Raghav's existing Customer; keeps links one-directional | Two-way links (Customer <-> Table/Order), simpler lookups but more coupling |
| 23 Oct | Added `chooseMenuItem(Menu)` and `calculateBill(int)` to Customer | Stage 2 VIP/Critic override these instead of the controller using instanceof (OCP) | Controller branches on customer type (violates OCP) |
| 24 Oct | GameController calls `stats.recordServed()` right after a successful `waiter.serve()` | Keeps Waiter free of scoring (SRP); the controller already sequences the step | Waiter calls `recordServed()` itself (Waiter would then depend on GameStats) |
| 24 Oct | Added `getServedTurn()` / `getReadyToPayTurn()` getters to Customer | Controller needs servedTurn to apply "finish eating the turn after being served"; Cashier needs readyToPayTurn for "pay the turn after" | Wrap `finishEating()` in try/catch (uses exceptions for normal flow, bad practice) |
| 24 Oct | Bad customer/order IDs are turned into `InvalidActionException` in the controller | Typos become a normal "try again" message instead of a crash, and no staff task is used up | Let `null` reach Waiter/Chef (NullPointerException) |
| 28 Oct | Staff methods call `checkCanAct()` first, then the role's own checks, and `markActed()` last | A rejected choice never uses up the task; "already acted" is reported before anything else | Mark acted first and undo on failure (easy to forget the undo) |
| 28 Oct | `Table.assign()` throws `IllegalStateException` if occupied, even though `Waiter` checks `isFree()` first | Manager mistakes are `InvalidActionException` (caught in Waiter); this is only a safety net for programming bugs | Trust callers and silently overwrite the occupant |
| 28 Oct | `GameStats` derives the paid count from the list of paid satisfactions instead of a separate counter | Count and average can't get out of sync | Separate `paidCount` field |
| 28 Oct | `Cashier` marks itself as acted after a payment and skips if it already acted | Uses the same one-task-per-turn rule as Waiter/Chef, so "one payment per turn" lives in `Staff` | A separate flag inside Cashier |
| 29 Oct | `Restaurant.customerLeft(c)` does the departure clean-up; `Cashier.processNextPayment(restaurant, turn)` looks up the order/table through `Restaurant` | Cashier and GameController were both searching the order and table lists, so the same logic lived in two places and both knew how Restaurant stores data | Customer holds its own Table and Order (two-way links, rejected on 23 Oct) |
| 29 Oct | `ConsoleUI.showFinalResult` gets pass/fail from `Objective` instead of re-checking 4 / $45 / 60 | Keeps the win rule in one class, as decided on 22 Oct; the UI had drifted from that | Leave the numbers in the UI (two places to edit if targets change) |
| 29 Oct | `Customer` state transitions are `final` | Every customer type must follow the same flow (brief 4.2); `final` makes the LSP claim enforced by the compiler | Rely on teammates not overriding them |
| 29 Oct | Removed unused methods (`getActiveOrders`, `getAllOrders`, `Menu.getItems/createDefault`, `hasLeft`, `hasPaid`, `getRoleName`) | Unused code clutters the class diagram, which must match the code | Keep them "just in case" |
| 29 Oct | `ConsoleUI.readInt()` strips the byte-order mark (U+FEFF) from each line | Windows PowerShell adds it when piping a test script with `Get-Content`, which shifted every scripted answer by one | Tell users not to pipe from PowerShell (easy to miss; a TA on Windows would hit it) |
| 29 Oct | `MenuItem` and `Order` identity fields are `final` | The compiler now enforces "bill locked at creation", instead of relying on there being no setters | Leave them non-final and rely on convention |
| 29 Oct | UML kept as PlantUML source in `docs/uml/`, with fields that point at other classes drawn as associations, not repeated as attributes | Text diffs cleanly in Git; avoids showing the same link twice | draw.io / Visual Paradigm files (binary, hard to review) |
| 29 Oct | GameController resets every staff member at the start of each turn, before any step runs | Guarantees the one-task-per-turn rule restarts cleanly; no step can forget to reset | Each staff member resets itself after acting (easy to miss when an action fails) |
| 29 Oct | Stage 2: the Critic always orders the most expensive dish (Pasta) by overriding `chooseMenuItem()` | Uses an existing hook, so no turn-logic changes; Pasta takes 2 units and the Critic loses 12 per turn, so it is the customer you can least afford to neglect | Critic reacts to service (a bad review lowers everyone's satisfaction); needs a new hook and `GameController` changes |
| 29 Oct | Stage 2: arrival 2 (turn 4) is the VIP and arrival 4 (turn 10) is the Critic; the rest stay Regular | The brief allows replacing two Regulars; still 6 arrivals, and spacing them apart shows each one clearly in the demo | Add the VIP and Critic as extra arrivals (changes the base setting) |
| 29 Oct | Stage 2: the VIP bill is `price * 90 / 100` in integer cents, after `super.calculateBill()` | Exact for every Stage 2 dish ($8.10, $13.50, $16.20); calling `super` keeps the parent's negative-price check (LSP) | `double` maths with rounding; repeating the check inside `VIPCustomer` |
| 29 Oct | Stage 2: each subclass names itself through an abstract `getTypeLabel()` on `Customer` | The UI can show "VIP" or "Critic" without `instanceof`, and a new type cannot forget its label (the compiler forces it) | `instanceof` in `ConsoleUI`; `getClass().getSimpleName()` (shows "VIPCustomer" and ties the display to class names) |
| 29 Oct | Stage 2: concrete customer classes are created only in `ArrivalSchedule`, from a `CustomerType` list in `GameConfig` | One creation point; which arrival is which type is configuration, so the turn loop never names a subclass | Create customers in `GameController`; a separate factory class (overkill for three types) |
| 29 Oct | Stage 2: `java -cp out control.Main regular` plays an all-Regular arrival list | The 3 Stage 1 scripts can be re-run on the Stage 2 build to show nothing broke (79.2 / 58.0 / 79.2) | Only point at the `stage-1` tag (shows the old build works, not that the new one still does) |
| 1 Nov | `CriticCustomer.chooseMenuItem()` uses a strict `>` when comparing prices, so on a tie the earlier menu item wins | Deterministic and simple; the Stage 2 menu has no equal prices, so it only matters if Stage 3 adds one | Break ties by prep units or pick the last item (extra rules nobody needs yet) |
| 5 Nov | Stage 3 turn order: arrivals, Happy Hour, Host, Waiter, Chef, eating and payment, waiting, end of turn (Happy Hour counts down last) | The Host is at the door, so the Waiter can take the order of someone the Host just seated in the same turn; a customer then loses 8 fewer points than with the Waiter alone, which gives the player a real reason to use the Host | Host acts after the Waiter (simpler, but the Host would only help when two customers arrive close together) |
| 5 Nov | Happy Hour recovery applies to customers who are WAITING, SEATED or WAITING_FOR_FOOD | The same three statuses that lose satisfaction at turn end, so one rule covers both directions; eating, ready-to-pay, paid and departed customers get nothing | A separate list of "waiting" statuses for recovery (two rules that could drift apart) |
| 5 Nov | The two combos are Salad + Pasta ($24.30, 3 units) and Burger + Salad ($21.60, 2 units), added to the end of the menu | Salad + Pasta is the brief's own example; adding to the end keeps the base menu's indexes, so the Stage 1/2 food rule is unchanged | Replace the base dishes with combos (breaks the earlier stages' results) |
| 5 Nov | No new combo-choice rule: Regular and VIP keep `menu[(id-1) % menu size]`, and the Critic keeps "most expensive", which is now Salad + Pasta | Combos are menu items like any other, so C4 and C5 land on them without new code | A "wants a combo" method on `Customer` and every subclass (more code, no gameplay gain) |
| 5 Nov | Happy Hour pricing goes through a `PricingPolicy` interface (`StandardPricing`, `HappyHour`) passed into `Waiter.takeOrder` | The Waiter must not know which discount is running (DIP); both implementations are real, so it isn't a checklist interface | The Waiter checks a Happy Hour flag itself (the Waiter would depend on Happy Hour) |
| 5 Nov | Bill = `pricing.applyTo(c.calculateBill(price))`: the customer's discount first, then Happy Hour | Matches the brief's VIP Burger example ($15.00 x 0.9 x 0.8 = $10.80) with no extra code | Apply Happy Hour first (same total today, but the brief states the order) |
| 5 Nov | Discounts round to the nearest cent with integer maths, `(cents * 80 + 50) / 100` | Money stays in `int` cents (brief 2.2); today's prices never produce half cents, but the brief asks for rounding | `double` maths with `Math.round` (floating-point error on money) |
| 5 Nov | Trade-off: `Host` repeats the Waiter's two seating checks | Keeps `Waiter`, a stable Stage 1 class, unchanged | An abstract `SeatingStaff extends Staff` with one `seat()` for both (removes the duplicate but changes Waiter's superclass to save about 6 lines) |
| 5 Nov | Trade-off: `HappyHour` holds both its state (used, turns left) and its price rule | One small class for one 2-turn feature | Separate `HappyHourPricing` and `HappyHourTimer` (cleaner SRP, twice the classes) |
| 5 Nov | Trade-off: the pricing policy is passed into `takeOrder` each time, not stored in the Waiter | The policy changes from turn to turn, so method injection fits better than constructor injection | A setter on the Waiter that the controller must remember to call every turn |
| 6 Nov | `Customer.recoverSatisfaction()` returns true only if satisfaction actually went up | The controller prints "recovers to N" from this result, so a customer already at 100 no longer prints "recovers to 100" | Return true for every eligible customer (the plan's sketch) |
| 6 Nov | Kept the old `Waiter.takeOrder(c, menu)` as a one-line wrapper using `StandardPricing` | `main` keeps compiling and playing exactly as Stage 2 between the Happy Hour merge and the controller merge; remove it once `GameController` passes the policy | Change the signature at once (breaks `main` until the controller branch lands) |
| 7 Nov | Removed the `takeOrder(c, menu)` wrapper once `GameController` passed the policy | Nothing called it any more; one way to take an order keeps the Waiter simple | Keep it as a convenience (dead code that would also have to go on the class diagram) |
| 9 Nov | `Main` takes `stage2` as well as `regular`; the Host and Happy Hour prompts are still asked in those modes | The six earlier scripts re-run on the Stage 3 build with `0` answered to the two new prompts, which shows nothing broke when the new features are unused | Hide the new prompts in the old modes (the old scripts would run unchanged, but that would test a different game loop from the one we ship) |
